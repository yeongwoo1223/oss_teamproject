# 팀 규칙(Team rules)

## 1. 작업 흐름

1. 모든 작업을 시작하기 전에 이슈 작성(이슈에는 변경 및 추가할 사항, 담당자를 작성)
2. 최신 `main`에서 브랜치를 작성
3. commit, push후 **무조건** PR을 진행한다. PR 본문에 Closes #번호로 머지 시 이슈가 닫히도록 하기
4. 리뷰 -> 수정 -> 리뷰 -> 승인 -> 머지 -> 브랜치 삭제 순으로 진행

## 2. 규칙

### 1. 브랜치 이름
- 형식: `<종류>/<간단한-설명>` (영어 소문자 작성, 단어가 띄어져있으면 하이픈)
- 종류:
    1. feat : 새로운 기능 추가
    2. fix : 버그 및 코드 수정
    3. docs : 문서나 docstring 추가 및 변경
    4. test : 테스트 사항 추가
    5. refactor : 유지보수 (기능 변경은 feat, 버그 수정은 fix)
    6. chore : 설정, 라이선스, 템플릿 같은 잡일

### 2. 커밋 메시지
- 형식: `<종류>: <한국어로 간단한 한 문장 정도>`
    - 예: `feat: 음정 전처리 추가`
- 커밋 하나에는 큰 틀의 변경 사항 하나
- 절대로 `32번째줄 fix`, `ㅁㄴㅇㄹ` 같이 정확한 의도를 알 수 없게 적는 것은 금지

### 3. PR 크기와 내용(중요)

- `PR 하나 = 이슈 하나 = 변경 하나` 가 되어야 함. 기능 추가와 버그 수정을 동시에, 혹은 이름 변경을 동시에 하는 것은 금지
- 변경 줄 수는 대략 100줄 내외로 처리.
- PR 제목 형식은 `<종류>: <한국어로 간단한 한 문장 정도>`
- 본문은 템플릿을 모두 채워야 함.

### 4. 리뷰

**리뷰어 수**
- 모든 PR은 무조건 2명 이상의 리뷰어 승인이 있어야 함.

**기한**
- 리뷰 요청 이후에 카카오톡으로 24시간 내에 언급
- 언급 후 다시 48시간 내에 해당 PR에 대한 리뷰가 있어야 함.

**댓글 달기 전 접두어**
- `nit:` 사소한 사항
- `suggestion:` 제안 사항
- `question:` 모르는 사항에 대한 질문(사사로 해도 괜찮으나 이력이 남는 것이 나을 듯 싶음)
- `blocking:` 반드시 고쳐야 할 것 같은 사항
- `etc:` 그 외의 사항

**리뷰어 확인 사항(참고)**
1. PR크기와 내용을 규칙에 있는대로 지켰는가?
2. 본인이 변경 사항을 이해했는가?(아래의 소통 항목에서 다시 확인)
3. 작성한 PR내용이 실제 변경 사항과 알맞은가?
4. `How I tested`에 실행 방법과 결과를 본인이 재현 가능한가?

### 5. 머지
- 승인이 완료되면 **PR을 올린 본인**이 머지를 진행
- 머지 방식은 **Create a merge commit** 사용
- 머지 조건:
    1. 2명 이상 승인
    2. 모든 `blocking:` 코멘트 해결
    3. 충돌(conflict) 발생 안함
    4. Actions 검사 통과

### 6. AI 사용(중요)
- PR 템플릿에 나와있는 것처럼 AI use에 들어가야할 항목이 존재

| 항목 | 내용 |
|---|---|
| 도구 | 어떤 도구를 썼는가 (예: ChatGPT, Claude, Gemini) |
| 위치 | 어느 파일, 함수, 줄 범위에 썼는가 |
| 방식 | 생성 / 자동완성 / 리팩터링 / 설명 / 리뷰 |
| 사후 | 본인이 직접 고치거나, 지우거나, 확인한 것 |

- AI 사용이 없으면 `None` 작성
- AI 사용 형식을 지키지않으면 서로 코멘트로 `blocking:` 달아주기

### 7. 라이선스 규칙
- 새 라이브러리 추가 시 PR에 라이선스 작성
